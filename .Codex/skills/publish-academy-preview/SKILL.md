## Когда использовать

При «опубликуй проверочную версию», «дай новую ссылку после правок» или повторном preview этого проекта.

## Как работать

1. В начале ответа кратко сообщи, что использовал skill `publish-academy-preview`.
2. Проверь рабочую ветку и diff, сохраняй посторонние изменения. Запусти тесты затронутого scope и TypeScript; UX audit до публикации. Не объявляй полный gate без шкалы и визуальных проверок.
3. При изменении DB используй только узкую additive migration. Без db push, дампов секретов или перезаписи пользовательских событий. Bootstrap прав должен быть одноразовым, не восстанавливать снятые роли на каждом build.
4. Публикуй через `pnpm exec vercel deploy --prod --skip-domain --yes --no-wait --scope igorsibola`. Для проверенной узкой миграции допустим отдельный `--local-config`. Основной домен не переключать без отдельного решения о релизе.
5. Дождись `vercel inspect <host> --scope igorsibola --wait`: только Ready означает готовность, первоначальная строка deploy её не доказывает. При Failed сначала прочитай build diagnostics.
6. Проверь активное firewall правило по projectId `prj_0TbNYlfHDmoAdFLI3keXtz3wH39F`, id `rule_block_retired_deployments_after_session_reset_jOeTYB`. Добавляй точный новый host, сохраняя остальные правила. Изменение доступности прежних адресов отдельно обосновать/согласовать, не делать автоматически.
7. Проверь публичную страницу/login HTTP и серверный auth redirect. Сохрани технические ограничения, git commit/push только своих файлов. Дай точную новую ссылку; разные preview домены не разделяют cookie.

## Структура результата

Новая ссылка, что проверено, что требует входа/визуальной проверки, сохранность данных.

## Правила

Не придумывай результат проверки. Не показывай keys/env values. Навигация чужого открытого браузера не должна потерять несохранённый ввод. Preview не означает разрешение на production promotion или снятие firewall защиты.
