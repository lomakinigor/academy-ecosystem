# Академия Светлова: MVP и целевой продукт

**Актуально на 9 октября 2026 года.** Этот документ — фактический срез репозитория `academy-ecosystem`. Он отделяет работающий MVP от заложенных, но ещё не реализованных модулей.

## 1. Что это за продукт

«Интеллектуальная экосистема Академии Развития Человека им. В. Ю. Светлова» — единая операционная платформа Академии. В целевом состоянии она управляет расписанием и записью на мероприятия, ролями и филиалами, обучением и ростом слушателей, финансами, рефералами и коммуникациями.

Ближайшая практическая ценность уже работающего MVP — убрать расписание из ручных сообщений и дать сотрудникам единый интерфейс для публикации и ведения событий, а слушателям — понятную страницу расписания и запись.

## 2. Точка остановки: текущий MVP

### Результат MVP

Сейчас развёрнуто web-приложение с публичным расписанием и административной частью. Оно подключено к PostgreSQL в Supabase и размещено в Vercel.

| Область                  | Состояние         | Что именно работает                                                                                                                                      |
| ------------------------ | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Публичное расписание     | Готово            | Главная `/`: список опубликованных событий, фильтры по периоду, направлению, филиалу, формату, поиску и имени спикера.                                   |
| Карточка события         | Готово            | `/event/[id]`: описание, время, формат, спикер, филиал, цена, вместимость и CTA записи.                                                                  |
| Регистрация и вход       | Готово            | Email + пароль, авто-вход после регистрации, сессия JWT на 7 дней. Telegram/OAuth нет.                                                                   |
| Запись на событие        | Готово            | Создание/отмена брони; повторное нажатие идемпотентно; при заполнении лимита — лист ожидания.                                                            |
| Админ-календарь          | Готово            | `/admin/calendar`: agenda-вид, фильтры, создание, редактирование и удаление событий.                                                                     |
| Пакетный ввод            | Готово технически | Свободный текст разбирается через OpenRouter/DeepSeek, затем сотрудник подтверждает отредактированные строки. Для production нужен `OPENROUTER_API_KEY`. |
| Спикеры                  | Готово            | `/admin/speakers`: список, добавление, переименование и исключение из списка спикеров.                                                                   |
| Личный кабинет слушателя | Минимальный       | `/student`: ближайшие 30 дней доступных событий; профиля, истории и прогресса пока нет.                                                                  |
| Инфраструктура           | Готово            | Turborepo, Prisma, tRPC, Zod, Vitest, GitHub Actions, Vercel-совместимая Prisma-конфигурация.                                                            |

### Главные пользовательские сценарии

1. Гость открывает расписание, фильтрует события и читает страницу конкретного мероприятия.
2. Гость регистрируется по email и паролю, автоматически становится слушателем.
3. Слушатель записывается на доступное событие; при лимите получает статус листа ожидания; может отменить запись.
4. Администратор филиала входит в `/admin/calendar`, видит доступные своему филиалу и общеакадемические события, создаёт/редактирует/удаляет их.
5. Администратор вставляет текстовое расписание, проверяет AI-разбор, при необходимости сопоставляет или создаёт спикера и сохраняет выбранные события.

## 3. Роли и границы доступа

У одного пользователя две независимые оси: административная роль определяет доступ к разделам и филиалам, академический уровень — доменные возможности и статус в Академии.

| System role                       | Доступ MVP                                                    |
| --------------------------------- | ------------------------------------------------------------- |
| `PRESIDENT`, `VICE_PRESIDENT`     | Все филиалы и общеакадемические события.                      |
| `BRANCH_DIRECTOR`, `BRANCH_ADMIN` | Админ-календарь и операции только в своём филиале.            |
| `STUDENT`                         | Личный кабинет, публичные события и собственные бронирования. |

Академические уровни: `FOUNDER`, `MAGISTER`, `MASTER`, `LISTENER`. Спикер — это флаг `is_speaker`, а не отдельная роль. На уровне событий создание разрешено `BRANCH_ADMIN+` или академическому уровню `MASTER+`; write-операции дополнительно проверяют допустимый филиал.

## 4. Техническая конфигурация MVP

| Слой   | Реализация                                                                                              |
| ------ | ------------------------------------------------------------------------------------------------------- |
| Web    | Next.js 14, App Router, React Server Components.                                                        |
| UI     | Tailwind CSS, собственный пакет `@academy/ui`, брендовые токены, responsive agenda, Lucide.             |
| API    | tRPC v10 и Zod; Server Components используют server caller без лишнего HTTP round-trip.                 |
| Данные | PostgreSQL + Prisma; Supabase используется как managed PostgreSQL.                                      |
| Auth   | NextAuth v5 Credentials provider, bcrypt, JWT.                                                          |
| AI     | HTTP-вызов OpenRouter, модель `deepseek/deepseek-chat-v3-0324`, function calling для структуры событий. |
| Deploy | Vercel, `apps/web` как root directory; Prisma engine включён в serverless bundle.                       |
| CI     | GitHub Actions: CI, preview deployment, production deployment.                                          |
| Тесты  | Vitest: API, DB/schema/seed, UI и web. `pnpm typecheck` проходит для 6 задач Turbo.                     |

### Production-переменные

| Переменная           | Обязательность                            | Назначение                     |
| -------------------- | ----------------------------------------- | ------------------------------ |
| `DATABASE_URL`       | Обязательно                               | PostgreSQL/Supabase.           |
| `AUTH_SECRET`        | Обязательно                               | Подпись JWT и работа NextAuth. |
| `OPENROUTER_API_KEY` | Обязательно только для AI-пакетного ввода | Доступ к OpenRouter.           |

Секреты не хранятся в Git. При отсутствии `OPENROUTER_API_KEY` календарь и остальные функции работают, но пакетный ввод корректно возвращает сообщение о недоступной конфигурации.

## 5. Модель данных: что уже есть

### Активно используется MVP

- `User`: email, пароль-хеш, роли, академический уровень, филиал, телефон, флаг спикера.
- `Branch`: город, контакты, адрес, код входа, часовой пояс.
- `Event`: статусы (`DRAFT`, `PLANNED`, `ACTIVE`, `COMPLETED`, `CANCELLED`), 10 типов, онлайн/гибрид, место, цена/донат/бесплатно, вместимость, теги, программа.
- `Booking`: уникальная бронь пользователя на событие и статусы `CONFIRMED`/`WAITLIST`/`CANCELLED` и др.
- `SpeakerProfile`: биография, специализации и рейтинг; используется как задел для полноценного каталога спикеров.

### Есть в schema, но не оформлено в продукт

- `Payment` — платежи за бронирования, реферальные бонусы и выплаты исполнителям.
- `ExecutorBalance` — начислено, выплачено и ожидает выплаты.
- `MentorRelation` — связь наставника и слушателя.
- `AcademicRecord` — присвоение уровня, программы и примечания.
- `referral_code` / `referred_by` — основа реферальной программы.

Эти таблицы не означают готовый функционал: сейчас для них нет пользовательского интерфейса, бизнес-процессов, API-операций или интеграции с платёжным провайдером.

## 6. Что нужно укрепить перед расширением MVP

Это не новые «красивые» функции, а условия безопасной эксплуатации.

1. **Закрыть доступ к AI API по роли.** Endpoint AI-разбора проверяет только факт входа; его нужно ограничить правом управления событиями, иначе слушатель теоретически может расходовать AI-лимит.
2. **Усилить server-side RBAC спикеров.** UI спикеров закрыт `/admin`, но tRPC-операции создания/редактирования/исключения спикера должны сами проверять административную роль и принадлежность к филиалу.
3. **Сделать операции бронирования атомарными.** При одновременной записи на последнее место текущая схема count → create может допустить переполнение. Нужна транзакция или reservation policy.
4. **Ввести production migrations.** Сейчас репозиторий не содержит Prisma migrations; схема применяется через `db push`. До первого расширения данных нужно зафиксировать историю миграций.
5. **Убрать устаревшие зависимости и документы.** В `apps/web` остаётся пакет Anthropic SDK, но текущий AI-маршрут использует OpenRouter. Часть roadmap в `CLAUDE.md` также не отражает уже сделанные CRUD, booking и public calendar.
6. **Сменить seed-пароли и создать настоящих сотрудников.** Seed-учётные записи предназначены только для запуска; для реального использования нужны индивидуальные пароли и процесс восстановления доступа.

## 7. Полный целевой продукт

### Этап A — операционная надёжность и календарь 1.1

- Отдельные статусы публикации и модерация событий.
- Неделя/месяц/день наряду с agenda, корректное отображение часовых поясов филиалов.
- Участники события: список, подтверждение, лист ожидания, отметка посещения и экспорт.
- Уведомления о записи, изменении и отмене события.
- Публичные страницы спикеров и полноценные поля профиля.
- Базовый dashboard филиала: события, записи, заполнение, отмены.
- PWA: install, offline shell, web push.

### Этап B — CRM и образовательный контур

- Карточка участника: контакты, история мероприятий, посещаемость, заметки и сегменты.
- Воронка работы с новыми заявками и возвращающимися слушателями.
- Программы, курсы, занятия и траектория обучения.
- Менторские пары, цели, заметки и контрольные встречи.
- Академические записи и Promotions Report: подтверждение готовности к следующему уровню с прозрачной историей решения.
- Консолидированная аналитика сети для президента и вице-президента; изоляция филиалов для остальных.

### Этап C — деньги и партнёрская механика

- Интеграция российских платежей (например, ЮKassa) с webhook-подтверждением и возвратами.
- Платёжный статус бронирования, счета, чеки и сверка.
- Финансовый кабинет исполнителя: начисления, задолженность, заявки на выплату, аудит изменений.
- Реферальные ссылки, правила tiered-бонусов, защита от саморефералов и отчёты.
- Для PII и платежей: 152-ФЗ, политика хранения данных, rate limit, audit log, мониторинг ошибок и транзакционная целостность.

### Этап D — каналы и контент-фабрика

- VK Mini App как основной мобильный канал для РФ; Telegram Mini App/Bot — дополнительный opt-in канал; MAX — после уточнения его API-возможностей.
- Telegram/VK-боты: расписание, напоминания, deeplink на событие, статус записи.
- Очереди задач (BullMQ + Redis) для рассылок, retries и отложенных публикаций.
- AI-инструменты: не только разбор расписания, но и черновики анонсов, карточек, баннерных текстов и постов с обязательным human review.
- SMM-календарь и отправка в VK/Telegram; публикация только после согласования сотрудником.
- Supabase Storage для фото спикеров и обложек мероприятий.

## 8. Рекомендуемый порядок продолжения

1. Добавить `OPENROUTER_API_KEY` в Vercel и протестировать AI-пакетный ввод на реальном расписании.
2. Закрыть три security/reliability debt из раздела 6: RBAC AI, RBAC спикеров, атомарность бронирований.
3. Перевести schema на migrations и завести индивидуальные production-аккаунты.
4. Собрать dashboard филиала и управление участниками как следующий бизнес-ценный модуль.
5. Только после стабильного CRM-контура подключать оплату, рефералы, PWA и внешние каналы.

## 9. Явно не реализовано

Нет OAuth/Telegram-login, восстановления пароля и верификации email; нет платёжной интеграции, CRM, финансового кабинета, реферальных выплат, менторства, академических promotions, PWA, VK/Mini App, Telegram-бота, Redis/BullMQ workers, Supabase Storage, Sentry/Axiom и E2E Playwright-тестов.
