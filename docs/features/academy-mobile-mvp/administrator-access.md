# Владелец и один уровень администраторов

## Discovery

1. Владелец должен назначать и снимать администраторов самостоятельно.
2. Сейчас роли есть, но такого интерфейса и API нет; JWT хранит роль на 7 дней.
3. Только явно настроенный владелец назначает BRANCH_ADMIN или снимает до STUDENT. Других уровней в интерфейсе нет.
4. Пароли и филиальные метки не меняются; сохраняем четыре раздела админки, управление доступом — внутри «Клиенты».
5. Вместо email или общего мастер-пароля используем фиксированный server-only OWNER_USER_ID подтверждённой записи.
6. Риск ошибки — доступ постороннего к персональным данным. До настройки ID все операции владельца закрыты; удаление собственных прав запрещено.

## Acceptance

- Обычный администратор не назначает других администраторов ни через UI, ни прямым API-запросом.
- Владелец видит зарегистрированные аккаунты и меняет только system_role на BRANCH_ADMIN/STUDENT.
- Ручная карточка без email/пароля не становится администратором.
- Владелец не может лишить себя доступа. Новые owner ID нельзя назначить из API.
- Чтение актуальной роли из БД перед серверными запросами отменяет полномочия старой JWT-сессии после снятия роли.
- Нет автопривязки владельца по совпадению email. OWNER_USER_ID настраивается оператором после проверки существующего аккаунта.
- БД-схема не меняется; пароль, филиал, бронирования остаются прежними.

## Reliability review

Инструкция programming-patterns.md в указанном глобальном каталоге отсутствует. Используем перечисленные в AGENTS.md правила: ошибки БД закрывают доступ, смена роли — один атомарный update, нет внешних API/платежей, выборки ограничены нужными полями без хешей, секреты/PII не логируются, ручная настройка и проверка владельца отделены от релиза. Отдельные circuit breaker/monitoring не добавляем для этого локального DB-сценария.

Review пройден: роли/сценарии/негативные случаи ясны; миграции и мастер-пароли не нужны. План: red RBAC/refresh tests → API и UI → полный test/typecheck → commit/push. Rollback: revert code и restore изменённой роли вручную; массовой смены ролей нет.

## Активация

Проверка Supabase SELECT для указанного email: аккаунт в public.User не найден. Владелец сначала регистрируется сам; не создаём и не меняем пароль. После регистрации ID проверяется и настраивается OWNER_USER_ID. До этого функция закрыта. Развёртывание и выдача прав ещё не выполнены.

## Проверка и ограничения

- Red: отсутствовали owner API, refreshSessionUser, UI; middleware отклонял новую роль по старым claims.
- Green: полный API-набор 119/119, полный web-набор 135/135; typecheck API/web прошёл.
- Self-review: назначение — один условный updateMany только system_role, без чтения/изменения пароля и без филиальной миграции.
- HTTP tRPC и RSC caller используют async createContext с актуальными правами БД. Server helper/layout тоже перечитывает роль. Edge middleware /admin проверяет вход, не роль из старого JWT; окончательное решение остаётся на server layout/API.
- UI не даёт снять владельца, но защиту обеспечивает сервер. OWNER_USER_ID не берётся из email/JWT/input и не имеет default ID.
- Прямые API unit callers используют подготовленный Context; отдельные тесты проверяют refresh с удалённым пользователем, изменённой ролью и отказом DB.
- Новый аккаунт владельца не создан, password не менялся, OWNER_USER_ID в production не настроен. Не считать функцию активированной или прошедшей ручную production-проверку.
