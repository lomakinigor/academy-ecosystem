# Безопасная регистрация: защита ручных карточек

Статус: отложено владельцем в конец web-работ 13 октября 2026. Runtime-код не менялся, незавершённый red-тест снят. Обязательный блокер основного релиза остаётся; следующий приоритет — мобильный UX.

## Discovery

1. Клиентская карточка может содержать бронирования и другие персональные данные; совпадение введённого email не доказывает право на неё.
2. Сейчас signup заменяет email/пароль существующей карточки, найденной через UserContact.
3. Не изменять найденную карточку и не входить в неё без доказательства владения.
4. Email verification инфраструктуры нет. Не добавляем новые внешние API или ключи; Telegram отложен.
5. Временный безопасный вариант — отклонить конфликт регистрации с понятным обращением к администратору. Автопривязка после подтверждения email — отдельный шаг, не реализуется молча.
6. Цена ошибки — раскрытие PII и захват существующей карточки; при ошибке БД не пытаться обходить проверку или регистрировать заново.

## Spec и acceptance

- Совпадение email-контакта не вызывает user.update, user.create, signIn или redirect.
- Пользователь видит сообщение о необходимости связаться с администратором; чужие имя/ID/контакты не выдаются.
- Новый email без совпадений создаёт новую карточку прежним путём и сохраняет callbackUrl мероприятия.
- Существующий аккаунт с email не заменяет пароль.
- База/схема/роли/production-данные не изменяются этой правкой. Совпадение не создаёт дубликат.
- Это защитный промежуточный этап, а не завершённая автоматическая активация ручной карточки. До реализации verification некоторые ранее заведённые клиенты не смогут зарегистрироваться самостоятельно с совпадающим email.

Review пройден: риск понятен, сценарии/ограничения/backward compatibility описаны. План: заменить старый небезопасный тест и добавить негативные сценарии → red → минимальное удаление update-ветки → полный web-набор/typecheck → commit/push.

Rollback: не возвращать небезопасную привязку; при проблеме временно отключить signup или сохранить отказ на совпадение. Функционал подтверждённой привязки проектируется отдельно.
