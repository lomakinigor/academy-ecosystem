# Рабочее пространство мероприятий — вариант для согласования

## Problem / discovery

1. Владельцу нужны правильный статус и явные способы создания мероприятий.
2. Сейчас header показывает учебный уровень «Слушатель», меню без active state, пакетный ввод спрятан в модалке.
3. Требуется «Владелец» для configured owner, подсветка открытого раздела, ручное и пакетное создание в календаре.
4. Сохраняем роль DB и серверные проверки: owner определяется OWNER_USER_ID, не email; учебный уровень остальных не меняем. Mini App не трогаем.
5. Минимальный подход — использовать существующие модалки, не создавать второй редактор.
6. Риски: неверная подсветка вложенных маршрутов, присвоение статуса по email, мобильное переполнение. Покрываем тестами и browser review.

## Spec и review

Header: владелец получает отдельный видимый badge; остальные прежний AcademicBadge. Навигация подсвечивает точный маршрут и вложенные маршруты одного раздела, aria-current=page только на активной ссылке.

Мероприятия: две CTA «Пакетный ввод» и «Создать вручную», каждая открывает соответствующую существующую форму. На телефоне кнопки и поля не требуют широкой строки. Последние изменения weekly-calendar и batch review входят в проверочную сборку.

Шаблон ручной карточки: название, описание, тип; начало и окончание с днём недели и обзором выбранной недели; спикер (выбор/создание); формат и адрес/ссылка; стоимость и цена ₽, заметка о цене; максимум участников, теги. Никаких дополнительных обязательных полей. Это исходный вариант для согласования, не финальная утверждённая карточка.

DB/API/state contracts не меняются. Affected: admin layout/nav, calendar-content, event-form-modal. Тесты: owner/non-owner, вложенная навигация, обе модалки, прежние календарные tests, typecheck. Откат: вернуть UI-компоненты, без миграций. Spec review пройден: цель/edge cases/негативный сценарий/границы/проверки определены.

План: red tests → UI → tests/typecheck → UX review → отдельная проверочная сборка без смены основного домена → browser review → commit/push.
