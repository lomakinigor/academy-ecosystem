# Серверная проверка времени мероприятий

## Discovery / spec

1. Проблема: клиентская проверка не защищает от прямого API-запроса с неправильным интервалом.
2. Сейчас create/update допускают окончание раньше начала; старый тест ожидает DRAFT, хотя приложение создаёт опубликованное PLANNED.
3. Нужно end_at > start_at при создании и изменении (включая изменение только одной границы).
4. Сохраняем PLANNED по умолчанию и fallback +2 часа при отсутствии окончания. Схему БД и данные не меняем.
5. Альтернатива — только UI validation — недостаточна для API, поэтому проверяем серверный контракт.
6. Риск — partial update: сравнивать переданные границы с сохранёнными, а не требовать обе.

Acceptance: create равного/обратного диапазона отклонён до Prisma.create; update любой одной границы проверяется с существующей второй; название/цена редактируются без изменения времени.

Review пройден: цель и негативные сценарии ясны, статус сохраняет действующее поведение, scope ограничен временем. План: red API-тесты → минимальная валидация → полный API-набор и typecheck → отдельный commit. Откат — revert commit.

## Верификация

- Red: create с равными границами и два partial update теста не отклонялись до исправления.
- Green: полный API-набор 110/110; typecheck API и web успешно.
- Ожидание DRAFT заменено на действующий PLANNED в тесте, runtime-статус не менялся.
- Self-review: валидация create находится в input schema; partial update использует сохранённую вторую границу перед mutation. Не добавлены новые поля или изменения БД.
